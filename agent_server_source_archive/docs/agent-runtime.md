# Agent 运行时介绍

## 1. Agent 到底负责什么

可以把 Agent 理解成部署在机器人上的“任务执行中枢”。它位于用户界面、模型和真实设备之间：

- 面向用户，它接收文字、语音识别结果和图像；
- 面向模型，它整理出稳定、有限、带规则的上下文；
- 面向设备，它把模型意图转换成受控的工具调用；
- 面向系统，它保存哪些事情已经成功、哪些事情失败、下一步允许做什么；
- 面向开发者，它输出事件和轨迹，说明每一步为什么执行、结果是什么。

因此 Agent 的最终产物不是“模型生成的一段文字”，而是一个已经经过执行确认的任务结果。

入口类是 `agents/agent.py` 中的 `Agent`。它本身不负责具体医疗检索或导航，而是把以下几个部分组织起来：

```text
Agent
├── API                 访问 Router 后面的模型，并记录调用
├── Session             保存一个用户会话
├── VoiceMode           规定这一类任务如何开始和结束
├── CallRouter          把模型输出变成可执行命令
├── MCPManager          找到并执行实际工具
├── SkillManager        加载可以临时激活的技能
├── Harness/State       保存计划、步骤、事实和预算
└── Camera              按需提供图像
```

## 2. 从外部输入开始的架构

### 2.1 用户入口不是模型入口

用户可能通过三种方式进入 Agent：

1. 直接调用 `Agent.handle_input()`，适合单客户端或本地测试；
2. 通过 `handle_input_in_session()` 传入一个独立 `Session`，适合 Headless 服务为多个浏览器或设备隔离会话；
3. 通过 VoiceMode 的 WebSocket，浏览器发送音频/ASR 事件，VoiceMode 形成完整 utterance 后再调用 Agent 循环。

Headless 负责连接管理和 HTTP/WebSocket 外壳，Agent 负责任务逻辑。也就是说，浏览器断开不会改变“医疗查询如何执行”的规则。

### 2.2 Agent 初始化时做什么

`Agent.initialize()` 建立运行时：

1. 注册 `ALL_TOOLS` 中的工具；
2. 根据配置选择导航地点 profile，例如 basic 或 hospital；
3. 加载 `SKILL.md` 形式的技能；
4. 创建 VoiceMode 和 BenchmarkMode；
5. 初始化相机后端；
6. 通知命令解析器当前有哪些工具和技能。

这个过程完成以后，Agent 才知道“自己能做什么”。例如某个技能依赖的工具没有注册，整个技能会被跳过，而不会让模型看到一个实际执行不了的能力。

## 3. 每一个组成部分在架构中的位置

### 3.1 VoiceMode：决定一轮任务怎样运行

当前生产入口主要是 VoiceMode。它负责：

- 接收经过 ASR 的用户话语；
- 识别高置信度的医疗、导航、时间和系统状态请求；
- 为明确请求建立紧凑工作流；
- 在工作流需要模型判断时调用模型；
- 要求最终通过 `speak` 结束语音轮次。

VoiceMode 不是单纯的提示词集合。它包含一层确定性策略。例如用户说“带我去急诊室”，Agent 可以直接建立 `navigate → speak` 的步骤，而不是先让模型自由发挥。用户说“胸闷、左臂发麻怎么办”，则先建立医疗查询步骤。

VoiceMode 默认一轮最多 12 个循环；BenchmarkMode 用于可重复评测，默认最多 8 个循环，并更多使用确定性调度。

### 3.2 Session：一个人的长期会话

Session 是 Agent 的“记忆容器”。它记录：

- 会话 ID；
- 当前和历史用户/助手消息；
- 当前任务 ID 和外部轮次；
- 工具成功记录；
- 当前任务失败记录；
- 医疗追问是否等待用户回答；
- 当前 Harness 执行状态；
- 每次模型调用的 token、耗时和错误。

同一个 Agent 可以服务多个客户端，但每个客户端应该使用自己的 Session。Headless 调用 `handle_input_in_session()` 时会用锁暂时切换 VoiceMode 的 Session，执行完成后恢复原状态，防止两个请求同时覆盖共享状态。

### 3.3 API：Agent 与模型之间的边界

`agents/API/api.py` 中的 `API` 不负责业务判断，它负责把当前 Session 变成模型请求，并把模型响应变回 Agent 能处理的文本：

- 调用本地 Router 的 `/v1/chat/completions`；
- 发送 `x-session-id` 和 `x-clear-history`；
- 在请求前进行 token 预检；
- 收集 prompt token、completion token、缓存命中等信息；
- 把 OpenAI 原生 `tool_calls` 适配成当前 Agent 的工具标签；
- 记录失败请求和轨迹；
- 会话结束时释放 History 模型的 KV cache。

本地 Qwen History 模型具有进程级缓存，Agent 会串行化本地模型请求；远程 `deepseek-*` 请求可以使用有界并发。这样做不是为了限制业务并发，而是为了避免本地物理 KV 状态被两个请求交错修改。

### 3.4 PromptSlots：模型看到的上下文

模型并不会直接读取 Session 对象。Session 会把信息编排成五个固定槽位：

| 槽位 | 生活化理解 | 放什么 |
| --- | --- | --- |
| `system` | 永远不变的工作手册 | 身份、工具规则、医疗安全规则、播报规则 |
| `conversation` | 之前的普通对话 | 需要让模型理解的对话背景 |
| `user` | 当前任务工单 | 用户原话、task_id、传感器、外部上下文、执行约束 |
| `history` | 已确认完成的工作单 | 已成功的工具、结构化结果、历史执行事件 |
| `attempt` | 当前故障单 | 最近的格式错误、非法参数、工具失败和修复提示 |

关键点是：`history` 只写入成功提交的动作，`attempt` 只记录当前任务最近的失败。模型因此能够区分：

```text
“已经成功导航到药房”
和
“上一次导航参数不合法，没有执行”
```

这比把所有原始对话简单追加到一个 messages 数组中更适合真实设备任务。

### 3.5 HistoryLedger：保留事实但限制模型上下文

HistoryLedger 会归档每一次成功的工具调用，但只向模型展示一个有界尾部，默认最多 8 条。完整记录可以进入轨迹，模型只需要看到与当前任务有关的摘要。

医疗历史更加谨慎：跨任务显示时，完整医疗事实会被压缩成状态、意图、证据数量和追问数量。下一次医疗追问需要通过 `pending_dialogue` 重新查询，而不是让模型仅凭旧摘要继续推断。

### 3.6 CallRouter：把模型文字变成动作

模型可能输出普通文字、`<tool>...</tool>`、技能调用或旧版 `act` 包装。CallRouter 负责：

1. 找到工具标签；
2. 解析 JSON 或兼容的旧格式；
3. 检查是否恰好只有一个命令；
4. 修复极少数尾部缺括号的截断输出；
5. 根据当前注册表匹配工具/技能名称；
6. 把无法解析的内容交给 `attempt`，要求模型修复。

CallRouter 只负责“看懂模型说了什么”，不直接决定这个动作是否允许。是否允许要由执行策略和 Harness 再判断。

### 3.7 MCPManager：执行真实能力

MCPManager 是工具目录和执行器。当前工具包括：

- `medical_consult`：把完整用户问题交给医疗咨询与检索链路；
- `navigate`：启动或停止机器人导航；
- `get_time`：取得当前时间；
- `get_system_stats`：取得系统资源状态；
- `speak`：把确认后的文本交给语音输出；
- `query`：在医疗工具明确需要补充信息时提出追问；
- `plan`、`act`：计划/旧协议兼容能力。

工具统一实现 `Tool.call(params, context)`，返回 `ToolResult`。返回值中：

- `data` 是给模型和用户看的业务结果；
- `facts` 是 Harness 可以信任并推进步骤的事实；
- `error/retryable/recovery_hint` 用于失败恢复；
- `diagnostics` 只用于诊断；
- `transient` 只在当前进程传递，例如录音 PCM，不能写入 prompt。

### 3.8 Harness：阻止模型越权推进任务

Harness 是 Agent 中“确认现实状态”的部分。它维护：

- 当前计划和活动步骤；
- 步骤依赖；
- 工具产生的事实；
- 任务预算和重试次数；
- 当前状态，例如 `GOAL_SATISFIED`、`BLOCKED`、`FAILED`；
- 最后一次动作和观察结果。

模型只能提出动作，不能自己写入“已完成”“已到达”或“查询到某疾病”。只有工具成功返回的 facts 才能推进 Harness。这是系统防止模型把承诺当成事实的关键。

### 3.9 SkillManager：把流程知识临时装入上下文

技能是目录中的 `SKILL.md`，不是一个隐式的模型能力。它有名称、适用模式、使用时机、安全级别和允许工具。执行层激活技能后，技能正文才会加入 prompt；当前外部轮次结束时会清除激活状态。

例如一个房间探索技能可以告诉模型如何观察、规划和移动，但真正的移动仍必须通过已注册的 `navigate` 工具，并受到 Harness 校验。

## 4. 一轮任务是怎样完成的

无论任务简单还是复杂，主循环都遵循同一条主线：

```text
接收输入
  ↓
建立/恢复 Session
  ↓
创建 task_id，准备五个上下文槽位
  ↓
判断是否有高置信度确定性工作流
  ├─有：直接调度可靠的工具步骤
  └─没有：让模型提出计划或动作
  ↓
解析一个动作
  ↓
执行策略 + Harness 校验
  ├─拒绝：记录 attempt，下一轮要求修复
  └─允许：调用 MCP/Skill
             ↓
      更新 facts、步骤和历史
             ↓
   需要下一步？回到模型/调度器
   需要用户补充？以 query 暂停
   已完成？调用 speak 结束
```

系统要求一次只处理一个动作。这样每次工具结果都能明确对应到一个步骤，失败也不会出现“其中一个动作成功、另一个动作失败但模型把两个都说成成功”的情况。

## 5. 正式运行示例：医疗咨询、追问和导航的组合任务

下面用一个真实运行中常见的复杂任务说明组件如何互动。假设用户对机器人说：

> “我胸口闷，左胳膊有点麻，应该怎么办？如果需要急诊，带我去急诊室。”

### 第一步：输入进入 Agent

如果来自语音，浏览器先把音频交给 ASR。Headless/Voice 得到文本后，会在内部加上“语音识别可能不准确”的提示，但 Session 保存的用户原话仍然是用户真正说出的内容。

Agent 创建本轮 `task_id`，保留之前的会话上下文，并把用户原话放进 `user` 槽位。由于同时出现胸闷、麻木、怎么办和带我去急诊，VoiceMode 的高置信度判断会识别出：

- 需要 `medical_consult`；
- 需要 `navigate`；
- 医疗查询必须先于导航；
- 最终必须 `speak`。

它建立类似下面的内部计划：

```text
s1  查询医疗证据              medical_consult
s2  根据任务要求启动导航      navigate       依赖 s1
s_followup  医疗工具要求时追问 query          条件步骤
s_final     根据已确认事实播报 speak          依赖前面步骤
```

注意：这个计划不是让模型自由编写的清单，而是 Agent 对明确生产意图建立的可验证执行骨架。

### 第二步：医疗工具查询

Agent 调用：

```text
medical_consult(query="我胸口闷，左胳膊有点麻，应该怎么办？如果需要急诊，带我去急诊室。")
```

医疗工具在 Agent 内部使用医疗安全策略和检索器；如果需要 dense 检索，它再通过 Router 访问 Embedding 服务。工具返回的不是一句模型猜测，而是结构化结果，可能包括：

- `status=urgent`；
- `red_flags`；
- `recommended_destination=急诊科`；
- `questions`；
- `evidence`；
- `medication_allowed=false`。

MCPManager 将结果交回 Mode。Harness 只把工具明确返回的内容写入 facts，例如 `medical.consultation`，并将成功调用提交进 `history`。如果查询失败，错误进入 `attempt`，不会伪装成医疗结论。

### 第三步：根据事实执行导航

在当前 VoiceMode 中，Agent 会先完成 `medical_consult`，再进入用户明确提出的 `navigate` 步骤；这是“医疗+导航”混合任务的固定顺序。医疗结果用于安全播报和事实 grounding，而不是让模型绕过医疗查询直接导航。若产品需要把“只有 status=urgent 才导航”作为硬条件，应把它配置为 Harness 的条件步骤；当前紧凑工作流本身主要表达“先查询、后导航”，并不把所有自然语言中的“如果”自动转换成医学条件。

导航工具会把口语目标映射为注册地点 `急诊科`，并根据真实 profile 检查这个地点是否可执行。

调用成功只能证明“已启动导航”，不能证明“已经到达”。因此 Harness 记录的是 `navigation.target=急诊科` 或“导航已开始”事实，后续播报不能说“已经到达急诊科”。

如果地点不在 profile 中，或设备执行失败：

- `navigate` 返回失败；
- Harness 状态变为 blocked/failed；
- Agent 不会继续假装移动成功；
- 最后仍可以调用 `speak` 如实告诉用户失败原因。

### 第四步：最终播报

所有必需步骤完成后，Agent 依据医疗 facts 和导航 facts 生成或调度 `speak`。医疗播报会经过 grounding 规则，不能加入工具没有返回的科室、疾病或药物建议。

合理的播报可能是：

> “检测到需要尽快处理的危险信号，建议立即前往急诊。我已开始为您导航到急诊科，请跟紧我。”

`speak` 成功后：

- 当前 execution event 记录 `FINAL_ACCEPTED`；
- 当前任务写入 ConversationTurn；
- VoiceMode 向浏览器/设备发送播报结果；
- Agent 发出 `turn_end` 事件并写入轨迹；
- 本轮结束，不再继续调用工具。

### 第五步：如果医疗工具需要追问

假设工具返回“需要知道症状持续多久”，而不是立即给出结论。此时 Agent 不能直接 `speak` 结束，而是调用：

```text
query(question="胸闷和左臂麻木持续多久了？")
```

`query` 会结束当前外部轮次，但不会结束 Session。Agent 保存 `PendingDialogue`，其中包含：

- 原始问题；
- 当前追问；
- 已执行工具；
- 后续继续使用的 `medical_consult`；
- 续问深度。

用户回答“刚开始十分钟”，下一次请求会把这句话和原始医疗问题合并后重新进入医疗查询，而不是把“刚开始十分钟”当成一个独立问题。这样跨多轮对话仍然保持医疗语义连续。

## 6. 模型何时参与，何时不参与

当前架构有意把确定性和生成式部分分开：

### 6.1 模型不需要参与的部分

- 明确的“现在几点”；
- 明确的“查看系统状态”；
- 已注册地点的明确导航；
- 高置信度的医疗查询入口；
- 已知步骤的工具参数构造。

这些动作由 VoiceMode 的紧凑工作流调度，减少一次模型调用，也避免模型漏调工具。

### 6.2 模型需要参与的部分

- 用户表达含糊，需要理解真实意图；
- 多个工具结果需要组织成自然语言；
- 没有被确定性规则覆盖的复杂任务；
- 需要根据当前 facts 选择下一步；
- 技能正文要求模型进行环境理解或流程判断。

在这些情况下，模型仍然不能直接修改现实状态。它只能提出一个动作，后面必须经过 CallRouter、执行策略、Harness 和 MCP。

## 7. 上下文如何避免无限增长

每次成功动作都会增加历史，每次失败也会增加修复信息。如果不做控制，多轮任务很快会超过模型窗口。因此 API 在每次模型请求前做 token 预检：

1. 使用本地 tokenizer 尽量复现 Server 的 ChatML 模板；
2. 预算按 `context_window_tokens - 2` 计算；
3. 先减少旧任务 history；
4. 再只保留最新执行事件；
5. 再减少失败 attempt；
6. 最后截短旧 conversation；
7. 保留 system、当前 user 和最新权威执行状态。

如果仍然放不下，Agent 在发送 HTTP 请求前记录 `PROMPT_CONTEXT_LIMIT`。这比让后端收到必然超限的 prompt 更容易定位。

## 8. 工具失败时系统如何表现

工具失败不等于整个 Agent 进程崩溃。失败一般经历：

1. MCPManager 捕获异常并返回失败的 `ToolResult`；
2. Agent 记录 `tool_result` 事件；
3. Harness 记录失败原因、是否可重试和当前步骤；
4. PromptSlots 把最近失败写入 `attempt`；
5. 若可恢复，下一轮要求模型修正参数；
6. 若达到动作预算、重复失败或安全条件不满足，则进入 `BLOCKED/FAILED`；
7. Agent 用 `speak` 如实结束，禁止把失败动作播报成成功。

连续工具失败达到上限时，系统会停止继续尝试，避免机器人重复执行物理动作或持续消耗模型资源。

## 9. 观测一轮任务

一轮任务会产生两类信息：

- 发往 Router 的实时 Agent 事件：`turn_start`、`model_start`、`model_output`、`tool_call`、`tool_result`、`harness_state`、`policy`、`final_output`、`turn_end`；
- 写入轨迹的完整记录：prompt slots、模型 usage、工具结果、压缩动作、耗时和最终结果。

事件只用于观察，不参与任务执行。Router 不可用时，Agent 只记录告警，不让观测系统故障影响用户任务。

## 10. 扩展 Agent 的正确方式

添加一个新业务能力时，应按“能力、事实、规则、播报”四件事一起设计：

1. 在 `agents/MCP/tools/` 实现 `Tool`；
2. 定义参数和 `harness_metadata`，说明读写属性、幂等性、产生什么事实；
3. 在 `ALL_TOOLS` 注册，让对应 mode 能看到它；
4. 在 Harness 中确认该事实如何推进步骤；
5. 在 CallRoute/Mode 中增加必要的意图识别和安全限制；
6. 定义失败、超时、重复调用时的恢复行为；
7. 让 `speak` 只能引用工具真实返回的事实；
8. 添加一条完整任务测试，而不是只测试工具函数本身。
