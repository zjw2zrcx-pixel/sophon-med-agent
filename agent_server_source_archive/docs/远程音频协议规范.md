# remote-audio.v1 远程收音/放音协议规范

本文面向负责适配麦克风和扬声器设备的开发人员。设备作为 WebSocket 客户端连接 Agent 或局域网测试包，所有消息均为 UTF-8 JSON Text Frame，音频放在 Base64 字段中。

## 1. 连接与共同约束

- WebSocket 地址：`ws://<Agent或测试机IP>:<端口>/ws`。
- 协议版本固定为 `remote-audio.v1`。
- 每次 `speak`、`record`、`speak_and_record` 都有独立 UUIDv4 `operation_id`。
- 一个连接同时只能执行一个操作；必须按 `operation_id` 路由回执，迟到消息不能结束另一个操作。
- `seq` 从 0 开始连续增长。重复序号会被忽略，缺号会令操作失败。
- 播放数据是独立完整的 WAV；录音数据是 16 kHz、单声道、PCM S16LE，片段不得重叠。
- Agent 是录音停止判定方。设备收到 `record.stop` 后应停止麦克风、刷新尾片并完成操作。

设备连接后的第一条消息必须是：

```json
{
  "protocol": "remote-audio.v1",
  "type": "hello",
  "device_id": "room-101",
  "capabilities": {
    "operations": ["speak", "record", "speak_and_record"],
    "playback_formats": ["wav"],
    "record_format": {
      "encoding": "pcm_s16le",
      "sample_rate": 16000,
      "channels": 1
    }
  }
}
```

服务端返回 `hello.ack` 后才能发送监听音频或接收操作。协议错误统一返回：

```json
{
  "protocol": "remote-audio.v1",
  "type": "protocol.error",
  "operation_id": "可选",
  "error": {"code": "错误码", "message": "说明", "retryable": false}
}
```

## 2. 空闲热词监听

设备在空闲状态持续发送非重叠 PCM：

```json
{
  "protocol": "remote-audio.v1",
  "type": "monitor.audio",
  "stream_id": "本次监听流的唯一ID",
  "seq": 0,
  "audio": {
    "encoding": "pcm_s16le",
    "sample_rate": 16000,
    "channels": 1,
    "data": "BASE64"
  }
}
```

推荐每片 20–200 ms。Agent只在空闲状态做热词识别；操作和会话处理中收到的监听片会被丢弃，不支持热词打断当前会话。热词命中后 Agent 直接启动 `record`，不播放确认铃声。

## 3. speak

Agent先发送：

```json
{"protocol":"remote-audio.v1","type":"operation.start","operation_id":"UUID","operation":"speak"}
```

设备应立即返回 `operation.accepted`。随后 Agent 逐段发送：

```json
{
  "protocol":"remote-audio.v1",
  "type":"playback.chunk",
  "operation_id":"UUID",
  "seq":0,
  "chunk_count":2,
  "is_first":true,
  "is_last":false,
  "text":"第一段。",
  "audio":{"encoding":"wav","sample_rate":44100,"channels":1,"data":"BASE64"}
}
```

设备必须按序播放，不得把“收到最后一片”等同于“播放完成”。最后一片在扬声器上实际结束后发送：

```json
{"protocol":"remote-audio.v1","type":"playback.completed","operation_id":"UUID"}
```

服务端随后发送 `operation.completed`。在此之前模型侧 `speak` 工具不会返回成功。

## 4. record

`operation.start` 中 `operation` 为 `record`，并携带录音格式、最短时长、静音时长、最长时长和 `stop_authority=server_webrtc_vad`。设备返回 `operation.accepted`，打开麦克风后发送 `record.started`，再持续发送：

```json
{
  "protocol":"remote-audio.v1",
  "type":"record.chunk",
  "operation_id":"UUID",
  "seq":0,
  "is_first":true,
  "is_last":false,
  "audio":{"encoding":"pcm_s16le","sample_rate":16000,"channels":1,"data":"BASE64"}
}
```

服务端以 WebRTC VAD 判定边界：最短 2 秒、语音后连续静音 1.5 秒、最长 10 秒。停止消息为：

```json
{"protocol":"remote-audio.v1","type":"record.stop","operation_id":"UUID","reason":"silence"}
```

设备收到后应在 2 秒内：停止采集；发送最后一个 `is_last=true` 的非空音频片；发送 `record.completed`。服务端拼合完整 PCM 后才发送 `operation.completed`。

## 5. speak_and_record

整个操作只使用一个 `operation_id`。播放消息与 `speak` 相同。设备在最后一片实际播放结束时必须依次完成：

1. 发送 `playback.completed`；
2. 立即打开麦克风；
3. 发送 `record.started`；
4. 按 `record` 规范发送音频。

服务端不会再发第二条 record 启动命令。若 `record.started` 早于 `playback.completed`，操作以 `RECORD_STARTED_EARLY` 失败。

### 5.1 Agent `query` 工具映射

模型侧工具名为 `query`，参数只有 `question`。它不是 MCP 网络工具；执行时由 Agent 映射到本协议的 `speak_and_record`：

```json
{"question":"症状持续多久了？"}
```

模型原始问题保留在工具参数和轨迹中，实际 TTS 文本为：

```text
症状持续多久了。在滴的一声后开始回答
```

`query` 成功结束当前用户轮，但不结束对话 session。录音经过 Qwen3-ASR 后，以同一 session 的下一条 user 输入继续。每个 session 最多三轮；第三轮禁止继续 `query`，必须以 `speak` 播报并结束。`speak` 成功后 Agent 归档当前 session，恢复等待热词状态。

轨迹不保存 PCM/WAV/Base64，只保存 `operation_id`、音频时长、字节数、SHA256、VAD 停止原因和 ASR 文本。

## 6. 设备抽象行为

设备端可以用任意平台 API，实现等价于以下接口即可：

```text
await play_wav(wav_bytes)           # 返回时必须已经物理播放结束
await start_microphone(16000, 1)
async for pcm_chunk in microphone() # 连续、不重叠、PCM S16LE
await stop_microphone()              # 刷新硬件/驱动残留数据
```

设备应维护 `IDLE -> ACCEPTED -> PLAYING/RECORDING -> COMPLETING -> IDLE` 状态机。断线或本地错误通过 `operation.error` 返回，其中 `error` 包含 `code/message/retryable`。收到 `operation.cancel` 后停止硬件并发送 `operation.cancelled`。
