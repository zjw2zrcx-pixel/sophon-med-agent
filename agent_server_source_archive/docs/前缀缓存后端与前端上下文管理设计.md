# 前缀缓存后端与前端上下文管理设计

## 目标与结论

本系统的本地 Qwen3.5 history 后端可以保存 TPU 上的 KV 快照，并在下一次请求的 token 序列具有**完全相同的前缀**时恢复最长快照，只对新增后缀执行 prefill。它不是文本相似度缓存：哪怕语义相同，只要 prompt 模板、槽位顺序、序列化结果或前缀字符改变，就会退回到较浅检查点或冷启动。

要获得稳定收益，前端应把“一个仍在继续的用户对话”映射为一个稳定的后端 `x-session-id`；每次只提交本轮输入，由 Agent 维护有序且可控的上下文槽位。不要在每次请求重新创建会话、重排历史、重写系统提示或在稳定前缀中注入时间戳。

历史基准显示，完整负载中启用前缀缓存后，物理 prefill token 总量从 1,466,994 降至 372,266（减少 **74.88%**）；turn 级 E2E P50 从 78,959.7 ms 降至 40,231.9 ms（减少 **49.05%**，约 **1.96 倍**）。这不代表所有请求都有同等加速：首轮、会话重置、历史截断改变开头、模型/模板变化都会造成 miss。

## 后端实现

### 1. 请求协议与槽位

本仓库使用 `suha.v3`，槽位顺序固定，不能交换：

```text
system → conversation → user → history → attempt
```

| 槽位 | 内容 | 缓存策略 |
|---|---|---|
| `system` | 身份、工具描述、规则、技能说明 | 会话内字节稳定，通常命中最深的公共前缀 |
| `conversation` | 已结束的用户/助手自然语言对话 | 只在末尾追加；旧轮淘汰会改变开头并降低命中 |
| `user` | 当前用户请求、当前约束、待续对话信息 | 每个外部轮变化；同一轮执行过程中保持稳定 |
| `history` | 已提交工具事实与 append-only 执行状态事件 | 只追加，允许从旧检查点补齐新增事实 |
| `attempt` | 最近成功之后的失败、拒绝和修正 | 变化最频繁，通常只重算这一小段 |

客户端调用 `POST /v1/chat/completions` 时应携带：

```http
x-session-id: <同一逻辑会话的稳定随机 ID>
x-prompt-slots: suha.v3
x-clear-history: false
```

请求体使用 `prompt_slots`，而不是由浏览器拼接完整 `messages`。当前 `agents/API/api.py` 已按此方式发送；`agents/API/session.py` 用 `sort_keys=True` 和紧凑分隔符序列化结构化状态，避免同一对象因键顺序变化破坏前缀。

### 2. 快照与恢复流程

```text
浏览器/语音端
  └─ 稳定 Headless 会话 ─→ Agent Session（稳定 Session.id）
       └─ PromptSlots 渲染 suha.v3
            └─ history server /v1/chat/completions
                 ├─ token 化完整 prompt
                 ├─ 按 S/C/U/H/A 从深到浅验证精确 token 前缀
                 ├─ restore_snapshot(最长命中检查点)
                 ├─ 仅 prefill 未命中的 token 后缀
                 ├─ 在槽位边界 save_snapshot
                 └─ decode 输出并返回诊断字段
```

`server/prefix_cache.py` 的检查点位于各槽末尾：

```text
S = system，C = conversation，U = user，H = history，A = attempt / 完整 prompt
```

恢复的前提是检查点保存的所有 token 都是新 prompt 的精确前缀。槽位在末尾增长时可部分命中：例如恢复旧 `H` 后，只 prefill 新增加的执行事件；`attempt` 改动时通常恢复 `H` 并重算 attempt。若 conversation 做了滑窗并删除最早轮次，缓存会安全退回 `S` 或 cold，绝不会错误复用旧 KV。

### 3. 服务端配置、容量与释放

`server/config.toml` 的 history 服务已有如下关键配置：

```toml
max_sessions = 4
max_snapshot_bytes = 1073741824 # 1 GiB
```

每个活跃 session 最多保存 S/C/U/H/A 五个检查点。`ExactPrefixCacheManager` 同时受 session 数和 snapshot 字节预算约束；达到任一上限时按 LRU 淘汰其他 session，并对每个句柄调用 `release_snapshot`。

对话真正结束时，Agent/Headless 管理器应调用：

```http
DELETE /v1/cache/sessions/{x-session-id}
```

该端点会删除该 session 的所有 TPU 快照。语音 Agent 在 `speak` 结束、显式 reset 和 WebSocket 断开时已通过 `release_history_session_cache()` 做 best-effort 释放；若用户处于 `query` 追问状态，则必须保留相同 session，不能提前释放。

> 当前服务的 15 分钟 session 清理循环只删除 Python 侧的 `sessions` 登记，未显式调用 `prefix_cache.evict()`。生产上不应把它当作 KV 释放保证：应以会话结束端点主动释放，并建议后续把 TTL 清理改为同时执行 `prefix_cache.evict(sid, reason="ttl")`。

本地 history 模型的物理缓存是进程全局状态，API 对本地模型使用请求锁串行化访问，避免不同 session 在同一模型 history 中交错；这也是单卡/单并发场景最安全的使用方式。

### 4. 诊断与监控

在 benchmark 请求中，服务端返回以下字段，前端调试页和日志应按请求/轮次展示：

| 字段 | 含义 |
|---|---|
| `cache_hit`、`cache_event` | 是否命中及命中的 S/C/U/H/A 检查点 |
| `cache_match_mode` | `cold`、`exact`、`partial` 或 `disabled` |
| `logical_prompt_tokens` | 完整逻辑 prompt token 数 |
| `reused_prefix_tokens` | 由快照恢复的 token 数 |
| `physical_prefill_tokens` | 实际在 TPU 上重新 prefill 的 token 数 |
| `slot_tokens` | 五个槽各自的 token 数，便于定位膨胀来源 |
| `ttft_internal_ms`、`request_ms` | 首 token 延迟与后端请求耗时 |
| `stage_ms` | tokenizer、恢复、prefill、保存快照、decode 各阶段耗时 |
| `snapshot_count`、`snapshot_bytes` | 当前进程快照数量与占用，用于发现容量淘汰 |

建议同时记录两种不同的命中率，避免概念混淆：

```text
请求命中率 = cache_hit 的请求数 / 可缓存请求数
token 命中率 = Σ reused_prefix_tokens / Σ logical_prompt_tokens
prefill 降幅 = 1 - Σ physical_prefill_tokens / Σ logical_prompt_tokens
```

前两者反映“是否复用”与“复用了多少”；最后一个最直接反映 TPU prefill 工作量是否减少。

## 前端 Agent 的上下文管理规范

### 会话状态机

前端应区分浏览器连接 ID、展示用 trace ID 和后端 LLM session ID；只有最后者决定 KV 缓存归属。推荐状态机如下：

| 前端事件 | 后端 session 行为 | 缓存影响 |
|---|---|---|
| 打开新对话 / 第一次唤醒 | 创建一次 Agent `Session`，保存其 `Session.id` | 首次 cold，建立 S/C/U/H/A 快照 |
| 同一轮工具执行、TTS、重试 | 复用同一个 `Session.id` | 通常命中 U/H，只重算事件或 attempt 后缀 |
| `query` 后用户补充回答 | 继续原 session，附加 pending dialogue | 保留 C 和既有历史前缀 |
| 用户发送下一条正常消息 | 继续原 session，只传本轮文本 | 命中 C；本轮 user/historical event 后缀增量 prefill |
| 用户点“新对话”或 `speak` 明确结束 | `DELETE /v1/cache/sessions/{id}`，再创建新 ID | 主动释放，下一对话 cold |
| 页面断开 / 长时间闲置 | best-effort delete；服务端 LRU 兜底 | 不让无主快照挤占活跃会话 |

浏览器不应为了每次发送文本而新建 WebSocket 或 Headless 会话。反之，也不能把不同用户、不同隐私边界或不同模型版本复用到同一个 `x-session-id`；这既会污染上下文，也会造成 KV 数据隔离问题。

### 提高命中率的具体做法

1. 固定系统提示与模型配置。将工具 schema、身份、语言、模型版本、thinking 开关等放在 session 创建时确定的 `system`；不要按请求拼接当前时间、随机数、追踪 ID 或变化的设备状态。变化信息应放在 `user` 或 `attempt` 末尾。

2. 前端只传当前用户原话和必要本轮元数据。历史、工具结果、执行状态由 Agent 的 `PromptSlots` 维护。不要把 UI 上完整轨迹、TTS 状态、波形数据、重复的工具 JSON 再次注入 prompt。

3. 以 append-only 方式维护稳定前缀。完成轮次追加到 `conversation`；成功工具事实追加到 `history`；失败修复留在短小的 `attempt`。同一结构化对象必须固定字段顺序、空值表示和 JSON 分隔符。

4. 做“晚且确定”的压缩。当前实现优先减少旧 history 可见条数，再压缩旧执行事件、attempt，最后才截取 conversation 尾部。前端不要每轮重新摘要或删除中间轮次；一旦从头改写 conversation，最深缓存会失效。

5. 避免无意义的 clear。`x-clear-history: true` 仅用于显式“新对话”或本地 Session 被重建。普通热词重新唤醒、语音识别重试、TTS 结束都不应自动 clear，除非产品语义确实是结束对话。

6. 把会话结束定义清楚。`query` 代表等待用户回答，应保留缓存；`speak` 代表此次语音会话结束时可释放缓存。若产品希望支持自然的连续闲聊，可把 speak 改为短暂 idle 状态，并在超时/新会话按钮时再释放，而不是每句话都新建会话。

7. 保持请求串行。前端禁用同一 session 的重复发送按钮，或用单一请求队列保证前一模型调用、工具结果写入和下一调用的顺序。乱序写入会同时降低命中率并破坏 Agent 事实状态。

### 前端可见的缓存调试卡片

每次模型调用在“执行轨迹”气泡旁建议展示一行紧凑摘要，而不是原始 JSON：

```text
缓存：H 部分命中 ｜复用 3,992 / 5,517 token（72.4%）｜实际 prefill 1,525 token
耗时：tokenize 126 ms ｜恢复 8 ms ｜prefill 2,613 ms ｜decode 8,505 ms ｜TTFT 2,822 ms
```

若为 miss，明确显示原因推断（新会话、显式 clear、系统提示变更、上下文从头截断、LRU 淘汰或模型重启），并保留原始诊断供展开查看。不要只显示“连接中”或一个笼统的失败 JSON。

### 当前 history BModel 的完整负载结果

`qwen3_5history_prefix_cache`（262 次调用、255 次成功）记录到：请求命中率 **80.39%**，logical prompt 为 982,817 token，physical prefill 为 289,382 token，prefill 降幅 **70.56%**。turn 级 token 命中率均值为 **64.64%**，P50 为 **69.91%**；turn E2E P50 为 40,687.1 ms。

该组使用的模型/调用数与上表的 qwen3_5 对照组不同，因此可用于确认 history 后端的实际命中水平，不能与上表横向相减来得到“history BModel 的无缓存加速倍数”。

### 小样本 cold/hit 与旧正式配对结果

评测说明中的 1,784-token 短输出冒烟，cold 的内部 TTFT 为 3,977.6 ms、服务内 E2E 为 4,529.6 ms；完整 A 重放复用全部 1,784 token 后，TTFT 为 55.7 ms、E2E 为 604.8 ms。该案例 token 命中 100%，E2E 约 7.49 倍，只用于验证链路和输出逐 token 一致性，不可作为容量或平均延迟承诺。

同一说明还记录了另一批 history 核心样本：物理 prefill 相对逻辑 prompt 减少 53.4%，缓存命中率 66.7%，90 组同 prompt cold/A 配对的平均 E2E 加速比为 5.058 倍。这是严格重放配对的结果，和上文完整 Agent 的自然执行聚合指标应分别阅读。

## 验收清单

- 新会话首请求为 `cold`，随后同一轮工具链至少应命中 `U`、`H` 或 `A`。
- 下一条用户消息在不改变 system/conversation 开头时，至少复用到 `C`。
- 显式新对话后，旧 session 的 `DELETE /v1/cache/sessions/{id}` 返回成功，`/status` 的 `snapshot_count`/`snapshot_bytes` 相应下降。
- 连续超过 `max_sessions` 的不同 session 时，日志有明确 LRU 淘汰原因，且其他活跃 session 仍可安全 cold/rebuild。
- 前端每次调用都展示命中检查点、复用 token、实际 prefill、TTFT 和阶段耗时；页面刷新不会把旧轮轨迹并入新轮。
- token 命中率按会话、外部轮次和模型版本分别统计；不要将 cold 首轮与已预热重放混为单一平均值。

## 相关实现位置

- `server/prefix_cache.py`：精确 token 前缀匹配、快照保存/恢复、LRU 与诊断。
- `server/qwen3_5_history_server.py`：模型启动、`/status`、聊天端点及 cache session 释放端点。
- `agents/API/session.py`：`PromptSlots`、历史可见窗口、确定性序列化和上下文压缩。
- `agents/API/api.py`：`x-session-id`/`suha.v3` 请求头、单卡请求锁与释放调用。
- `agents/Headless/manager.py`、`agents/Headless/voice_agent.py`：浏览器语音会话到 Agent session 的生命周期管理。
